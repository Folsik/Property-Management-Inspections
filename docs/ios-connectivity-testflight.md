# Inspectly — iOS connectivity and TestFlight runbook

Status: **implementation prerequisites, NOT a claim of deployed staging or TestFlight upload**.

## Decisions and audited behavior

- `apps/ios/project.yml` generates Info.plist via `GENERATE_INFOPLIST_FILE=YES`.
  Camera and microphone purpose strings are generated by build settings. Do not edit
  generated Info.plist directly. `NSAllowsLocalNetworking` is only on Debug.
- Three configurations: **Debug** = localhost over HTTP only for Simulator;
  **Staging** and **Release** = explicitly configured HTTPS origin only.
  An unset URL is a deployment error, not a reason to select a different server.
- `APIClient` retains access JWT in memory and rotates the refresh token in
  ThisDeviceOnly Keychain, using a single actor/task for refresh. 401 from refresh
  revokes local credentials; network/5xx errors do not delete them. Logout uses
  server-side `/v1/auth/refresh/logout`; a network failure does not claim logout.
- The Go API and worker already have separate executables/Dockerfiles, a shared
  embedded migration runner using PostgreSQL advisory locks, an API `/healthz`
  readiness-style DB ping, and signal-based HTTP graceful shutdown. The API is
  HTTP **behind** a TLS terminator, not a public TLS endpoint by itself.
- Production mode (`APP_ENV` anything other than `development`) requires
  stable `JWT_PRIVATE_KEY` and PostgreSQL `sslmode=verify-full`; it does not
  return development OTPs. Public staging MUST use `APP_ENV=production`.
  Worker also validates TLS and database credentials in production mode.
- Production-equivalent HTTPS, independent staging DB/bucket, SMS provider,
  DNS/certificates, backup storage, physical device and Apple signing are NOT
  provided by this repository.

## Required service topology (provider-neutral)

    iPhone / TestFlight -> https://<staging-api-domain> -> TLS ingress/WAF
                                                    -> private Go API:8080
                                                    -> private PostgreSQL (TLS verify-full)
                                                    -> private worker (no inbound port)
                                                    -> S3/R2-compatible object storage

Provide a separate production deployment and secrets from staging. Prefer managed
PostgreSQL with encrypted automated backups, point-in-time recovery and tested restores.
Never publish DB:5432, worker, or S3 secret endpoints. Only inbound TCP 443 should be
public (plus 80 for certificate issuance if applicable); bind the private Go API
to an internal network or loopback. Preserve trusted ingress rules and edge rate
limiting on OTP, password and refresh routes; do not trust arbitrary forwarded IPs.
If using multiple Next.js replicas, coordinate refresh tokens per the auth session
documentation; the iOS client has its own actor-based protection.

**Provider selection checklist:** choose hosting only after confirming intended
region/data residency, PostgreSQL TLS CA and PITR capability, outbound Twilio reachability,
S3/R2-compatible presigned HTTPS URLs and CORS requirements, observability, edge WAF
and per-environment costs. DNS, TLS ingress, deployment identity and backups depend on
the selected host. No cloud account or domain is provisioned by this change.

## Environment variables and secrets (names only)

API required in staging/production:
`APP_ENV=production`, `HTTP_ADDR`, `DATABASE_URL`, `JWT_PRIVATE_KEY`,
`JWT_ISSUER`, `ACCESS_TOKEN_TTL`.
For live registration/SMS: `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`,
`TWILIO_FROM_NUMBER`. For verified email/invitations:
`RESEND_API_KEY`, `EMAIL_FROM`, `PUBLIC_WEB_URL`.
For media: `S3_ENDPOINT`, `S3_BUCKET`, `S3_REGION`,
`S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`.
For worker transcription only when enabled:
`TRANSCRIPTION_ENDPOINT`, `TRANSCRIPTION_API_KEY`.
For BFF trusted ingress if deployed: `TRUSTED_BFF_SECRET` and the documented BFF
environment/cookie security settings. Separate `DATABASE_URL`, bucket and
`JWT_PRIVATE_KEY` per environment. Persist each environment's signing key through
restarts and replicas. Inject credentials through the deployment secret manager,
never through the iOS app, committed .env or GitHub workflow logs.

If choosing a CI signing pipeline, additionally configure protected Apple
certificate/profile/App Store Connect API credentials in your CI provider;
these are NOT used by current unsigned simulator CI. iOS build setting
`INSPECTLY_API_BASE_URL` is **public configuration**, not a secret.

## Deploy and health verification sequence

1. Provision staging DNS, trusted TLS certificate, ingress, private PostgreSQL
   with `sslmode=verify-full`, isolated object bucket, SMS sender and secret
   manager. Restrict access to DB and worker. Disable development OTPs.
2. Restore a tested staging dataset or initialize an empty database, then start
   API/worker with `APP_ENV=production`. Both currently run embedded migrations
   under advisory locks at startup. Restrict deployments to compatible migrations
   and monitor application logs. Take a snapshot before schema changes.
3. Configure S3 endpoint as HTTPS with correct signing region/credentials and
   verify presign -> upload -> confirm plus object HEAD and download lifecycle.
   For browser BFF uploads, configure bucket CORS explicitly as required.
4. Probe `GET https://<staging-api-domain>/healthz`: expect 200 JSON only when
   PostgreSQL is reachable; expect 503 when DB unavailable. Configure ingress
   health probes accordingly; do not expose internal dashboards.
5. Test HTTPS certificate trust/chain from a physical iPhone; test TLS downgrade
   and untrusted certificates (requests must fail); confirm no sensitive data in
   ingress logs. Confirm edge WAF rate limits and Twilio delivery.
6. Verify shutdown via SIGTERM with in-flight API requests and worker jobs.
   Check DB reconnection, job retries, and no credentials regenerated on restart.

### Backup and restore acceptance

Schedule encrypted PostgreSQL backups with PITR where available; store in an
isolated account/region and enforce retention/access controls. Version and protect
object storage independently (DB backups alone do not restore photos/voice).
Maintain signing-key escrow in the secret manager. On a disposable staging DB:
restore the snapshot/PITR, run migration checks, compare row counts, verify
referenced media objects and authenticated inspection reads. Record RPO/RTO,
owner and date. **No backup/restore is verified until this drill is performed.**

## Simulator

On macOS with Docker/Go, start local `docker compose up -d --build` and check
`curl -f http://127.0.0.1:8080/healthz`. Then:

```sh
cd apps/ios
xcodegen generate --spec project.yml
xcodebuild -project Inspectly.xcodeproj -scheme Inspectly \
  -configuration Debug -destination 'generic/platform=iOS Simulator' \
  CODE_SIGNING_ALLOWED=NO build
```

Debug uses `http://localhost:8080` only. A physical device must **not** use
Debug/local networking: use Staging with reachable HTTPS.

## Physical iPhone (manual owner actions)

1. Confirm iPhone is iOS 17+, developer mode and device trust are enabled.
   Confirm the public staging API passes HTTPS/health/auth smoke tests.
2. In Xcode > Settings > Accounts, sign in to an authorized Apple Developer team.
   Configure the existing `com.inspectly.inspections` bundle identifier, team,
   device registration and provisioning according to your account. Change the
   bundle identifier **only** if it conflicts with an existing App ID.
3. Generate the Xcode project; select **Edit Scheme > Run > Build Configuration:
   Staging**. Supply `INSPECTLY_API_BASE_URL=https://<staging-api-domain>` as
   an Xcode build setting (e.g. a local untracked .xcconfig integrated in a
   local project specification, or via the xcodebuild command below).
   Never use an Xcode scheme environment variable to override a compiled URL.
4. Example device build (replace domain and signing team with **real** values):
   ```sh
   xcodebuild -project apps/ios/Inspectly.xcodeproj -scheme Inspectly \
     -configuration Staging -destination 'generic/platform=iOS' \
     INSPECTLY_API_BASE_URL=https://<staging-api-domain> \
     DEVELOPMENT_TEAM=<real-team-id> build
   ```
5. Install and exercise real SMS OTP -> registration/password -> login -> tenant
   data -> quit/launch -> refresh -> concurrent requests -> logout -> login.
   Deny/reallow camera and microphone permissions and test actual photo/audio
   upload/confirm. Check Keychain persistence on restart, and that transient
   airplane-mode failures preserve credentials. Run an unauthorized cross-tenant
   read and confirm 401/403/404, with no other tenant's data. Use test accounts.

## TestFlight archive and upload (manual owner actions)

1. In Apple Developer portal create/verify an App ID for
   `com.inspectly.inspections`, distribution certificate, provisioning and
   proper team access. Set an app record in App Store Connect with bundle ID,
   version/build number, testers, contact details and required compliance.
2. For **staging-backed TestFlight**, archive **Staging** with a real HTTPS
   staging origin. For production-backed App Store Release, archive **Release**
   with the production origin. Never use the CI-only example host.
   ```sh
   cd apps/ios
   xcodegen generate --spec project.yml
   xcodebuild -project Inspectly.xcodeproj -scheme Inspectly \
     -configuration Staging -destination 'generic/platform=iOS' \
     -archivePath "$PWD/build/Inspectly-Staging.xcarchive" \
     INSPECTLY_API_BASE_URL=https://<staging-api-domain> \
     DEVELOPMENT_TEAM=<real-team-id> archive
   ```
3. Inspect archived `Info.plist` URL/environment, signing entitlements,
   `NSCameraUsageDescription` and `NSMicrophoneUsageDescription`; ensure no
   localhost/invalid placeholders or secrets. Confirm App Privacy responses,
   privacy policy URL, required-reason API declarations and export compliance
   with counsel/reviewer before distribution. The repository does not establish
   these legal declarations on behalf of the owner.
4. In Xcode Organizer: Validate App -> Distribute App -> App Store Connect ->
   Upload, using your account's real distribution credentials. After Apple
   processes the build, add internal/external testers as allowed (external
   testing may require Beta App Review).
5. Verify a tester installs the app, can authenticate against intended backend,
   captures media, restarts and logs out. Do not declare TestFlight complete
   merely because an unsigned simulator build passed.

## Required checks and remaining blockers

- CI: XcodeGen, generated settings guard, unsigned Debug/Staging/Release
  Simulator builds; Go unit/integration and Compose smoke via existing PR jobs.
- Not verified by repository changes alone: physical device signing/installation,
  Apple credentials, iOS Keychain reboot handling, real Twilio SMS, deployment
  TLS/trusted domain, browser S3 CORS, real multi-request auth replay behavior,
  edge protections, cross-tenant live tests, PITR restore, archive validation,
  TestFlight upload and external beta approval.
- The CI-only HTTPS host is a **compile-time probe**, not a deployed service.
  Production builds must be supplied a real, explicitly chosen origin.
